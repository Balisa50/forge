## Training is the beginning; serving is the job
You trained FlightWise and wrapped it in a simple Flask API back in W4. This week you take serving seriously, because getting a model to serve predictions *reliably*, at low latency, at scale, with proper error handling, is the engineering challenge that occupies most of a production ML engineer's time. Training a model is the start; making it a dependable production service is where the real work lives, and it involves architectural decisions that are invisible in the model itself: synchronous versus asynchronous, single-instance versus distributed, online versus batch, request-level versus session state. This week you make those decisions deliberately and learn the tools, FastAPI, dynamic batching, TensorRT, Triton, that turn a model into a production-grade endpoint.

## Serving is architecture, not just a wrapper
The key shift this week is recognising that *how* you serve a model is an architecture decision with real trade-offs, not an afterthought. The same trained model can be served in fundamentally different ways depending on the requirements, and choosing wrong makes the service slow, expensive, or unreliable:
- **Synchronous vs asynchronous:** does the caller wait for the prediction (a real-time API), or submit a job and collect the result later (heavy batch work)?
- **Online vs batch:** do you predict one request at a time as it arrives (online, low-latency), or score millions of records in a scheduled run (batch, high-throughput)?
- **Single-instance vs distributed:** does one server handle the load, or do you need many behind a load balancer?
These are the same kinds of serving decisions you met in the AI-engineering deployment week, now for your own trained models, and the right answer depends on the latency, throughput, and cost the use case demands.

## FastAPI: the right starting point
**FastAPI** is the current standard for Python model serving, and for good reason: it is **async-first** (handles concurrent requests efficiently), generates **automatic API documentation** (OpenAPI), and **validates requests and responses** through Pydantic schemas, the same structured-validation idea from the AI-engineering track, here guarding your model's inputs. For most serving needs, one model, moderate traffic, FastAPI with the uvicorn server is the correct, simple starting point, a notable upgrade from the bare Flask of W4 (async, validation, and docs built in). Its limits appear in two situations the rest of the week addresses: when your model is **slow** (long GPU inference) and when you need **dynamic batching** to use a GPU efficiently. Knowing FastAPI is the right default, *and* knowing exactly when you outgrow it, is the practical framing of the week: start simple, escalate to specialised serving infrastructure only when the model's speed or scale demands it.

===D2===
## The serving patterns, and choosing among them
"Serve the model" is not one thing, it is a choice among patterns, and the right one depends on your latency, throughput, and cost needs. The main axes:
- **Online (real-time) serving:** predict one request at a time, as it arrives, with low latency, an API that answers in milliseconds. This is FlightWise's `/predict`: a user (or service) needs an answer *now*. Optimised for latency.
- **Batch (offline) serving:** score a large set of records all at once, on a schedule, where no one is waiting on any single prediction, recompute every user's churn score nightly. Optimised for throughput, not latency.
- **Streaming serving:** predict on a continuous stream of incoming events, between online and batch, for things like real-time fraud scoring on a transaction feed.
The same model can serve in any of these modes; the pattern is dictated by *how the predictions are consumed*, not by the model.

## Match the pattern to how predictions are used
The skill is reading the use case to pick the pattern, because choosing wrong wastes resources or fails requirements. If predictions are needed **interactively** (a user clicks and waits, a service calls and blocks), you need **online** serving with low latency, and batch would be useless (the answer arrives too late). If predictions are needed for **many records with no urgency** (a nightly report, pre-computing recommendations for every user), **batch** is far more efficient, processing everything in one optimised run is cheaper and simpler than a stream of online calls, and online serving would be wasteful overkill. A revealing pattern is **pre-computation**: if the set of possible inputs is known and bounded (recommendations for your existing users), you can *batch*-compute all the predictions ahead of time and serve them from a fast lookup, getting online-latency responses without online-inference cost, the right architecture is sometimes to not infer at request time at all. So you ask: who consumes the prediction, how fast do they need it, and how many are there? The answers point to online (interactive, low-latency), batch (bulk, no urgency), or pre-computed (bounded inputs, served from a cache), and getting this right is a bigger lever on cost and latency than any model optimisation.

## State: another dimension of the decision
A further serving distinction is **request-level vs session-level state**, which shapes the architecture. Most model serving is **stateless**: each request is independent and carries everything the model needs (FlightWise's `/predict` takes a flight and returns a probability, remembering nothing), which is the simplest and most scalable design, because any server can handle any request and you scale by just adding servers (the stateless property from W4). Some applications need **state across requests**, a session, a sequence of user actions, accumulated context, which is more complex because the serving system must track and route state (which server holds this session's data?), constraining how you scale. The guidance is to **prefer stateless serving** wherever possible, because it is dramatically simpler to scale and operate, and to introduce session state only when the use case genuinely requires remembering across requests, the same simplicity discipline from the rest of the track. Recognising the serving pattern (online/batch/streaming, stateless/stateful) that fits your use case is the foundational architecture decision of model serving, and it is mostly determined by *how predictions are consumed*, which is why you analyse that before writing any serving code.

## Where this fits
You understand the serving patterns, online (interactive, low-latency), batch (bulk, efficient), streaming, and pre-computation, plus the stateless-vs-stateful choice, and that the right pattern is dictated by how predictions are consumed. This architecture decision is the biggest lever on serving cost and latency. Tomorrow you handle the specific challenge of serving *slow* models efficiently on a GPU: dynamic batching.

===D3===
## The GPU serving problem, and dynamic batching
Serving a deep learning model on a GPU has a specific efficiency problem: a GPU is fast *per batch* but processing requests **one at a time** wastes most of its parallel capacity, you fire up thousands of cores to process a single input, then again for the next. Yet online serving receives requests one at a time, as users send them. **Dynamic batching** resolves this tension: the serving system *waits a few milliseconds* to collect several incoming requests, groups them into a batch, runs them through the GPU together in one efficient pass, and returns each result to its caller.
```text
without batching:  req1 -> GPU (wasteful), req2 -> GPU (wasteful), ...
dynamic batching:  collect req1,req2,req3 for ~5ms -> ONE GPU pass -> split results back
```
This gives near-batch GPU efficiency while still serving individual online requests.

## The latency/throughput trade it manages
Dynamic batching is a deliberate trade between **latency and throughput**, and understanding it is the point. Waiting to collect a batch adds a *small latency* to each request (it waits up to a few milliseconds for batch-mates), but it dramatically increases *throughput* (the GPU does far more useful work per unit time by processing many requests at once) and thus lowers cost per prediction (you need fewer GPUs for the same load). You tune two knobs, the **maximum wait time** (how long to wait for a batch to fill) and the **maximum batch size**, to balance the trade for your needs: a latency-critical service uses a tiny wait window (sacrificing some batching efficiency for speed), while a throughput-oriented service waits longer to fill bigger batches. The key insight is that dynamic batching lets you get *most* of the GPU's batch efficiency in an *online* (one-request-at-a-time) setting, which would otherwise be impossible, at the cost of a few milliseconds of added latency, usually a great trade for GPU-served models. This is exactly the kind of serving-infrastructure technique FastAPI alone does not give you, and it is why GPU model serving often needs the specialised servers (Triton) you will meet this week.

## Why this matters: GPU serving economics
The reason dynamic batching is a headline technique is **cost**: GPUs are expensive (the W14 lesson), and serving them inefficiently, one request per GPU pass, means you need many more GPUs (and dollars) to handle your traffic than you should. Dynamic batching can increase a GPU's serving throughput several-fold, directly cutting the number of GPUs and the cost to serve a given load, the inference-side echo of the training-efficiency-is-cost-efficiency lesson from W14. It is the single most important technique for making GPU model serving economical, which is why production deep-learning serving systems are built around it. For a CPU-served classical model (like FlightWise's XGBoost), batching matters less, but for any GPU-served deep model at real traffic, dynamic batching is often the difference between an affordable service and a ruinously expensive one. Recognising when you need it, GPU model, online serving, meaningful traffic, and that it is a latency-for-throughput trade you tune, is the practical takeaway, and it sets up *why* the specialised inference servers (Triton, next) exist: they provide dynamic batching and more as production infrastructure, so you do not hand-build it.

## Where this fits
You understand dynamic batching: collecting incoming requests into batches for efficient GPU inference, trading a few milliseconds of latency for several-fold throughput (and thus much lower cost per prediction), tuned via wait-time and batch-size. This is the core technique that makes GPU serving economical. Tomorrow you learn TensorRT, which speeds up the model itself before it even reaches the serving layer.

===D4===
## Making the model itself faster: TensorRT
Dynamic batching makes the *serving* efficient; **TensorRT** (and similar tools) makes the *model* itself faster, by optimising it for inference on the target hardware. A model as trained is not optimised for fast prediction, it carries training-time overhead and runs operations naively, and inference-optimisation compilers like TensorRT (NVIDIA's, for their GPUs) rewrite the model into a highly efficient form for serving:
```text
trained model  --TensorRT optimisation-->  optimised inference engine
  (techniques: layer fusion, precision reduction, kernel selection for the GPU)
  -> often 2-5x faster inference, same predictions
```
You convert the trained model once, and the optimised version serves predictions substantially faster, with no change to *what* it predicts, just *how fast*.

## What inference optimisation actually does
TensorRT's speedups come from a handful of techniques that are worth understanding because they reveal where inference time goes:
- **Layer fusion:** combine several consecutive operations into one (a convolution, a bias add, and an activation become a single fused operation), reducing overhead and memory traffic between steps.
- **Precision reduction:** run the model in lower precision (float16 or int8 via quantization) where accuracy permits, the mixed-precision and quantization ideas from W14, now applied to serving, fewer bits means faster math and less memory.
- **Kernel auto-tuning:** pick the fastest GPU implementation of each operation for the specific GPU you are serving on, since the optimal way to run an operation depends on the hardware.
- **Graph optimisation:** prune and simplify the computation graph, removing operations only needed for training.
The result is the *same model* (same architecture, same learned weights, essentially the same predictions) running 2-5x faster at inference, which directly cuts latency and serving cost.

## The trade-offs, and when it is worth it
Inference optimisation is powerful but not free, and knowing the trade-offs keeps you from over-applying it. The costs: it adds a **conversion/compilation step** to your deployment pipeline (you must convert and validate the optimised model), it can be **hardware-specific** (a TensorRT engine is tuned for a particular GPU, reducing portability), and aggressive **precision reduction** (especially int8 quantization) can slightly change predictions, so you must *validate* that the optimised model still meets your accuracy bar, the same "confirm quality survived the optimisation" discipline from the AI-engineering cost week. So you reach for inference optimisation when serving performance genuinely matters, high traffic where latency or GPU cost is significant, real-time requirements a naive model cannot meet, and you skip it when the model is already fast enough or traffic is low (the conversion complexity is not worth it for a low-traffic service). The judgement mirrors the whole track's efficiency theme: optimise the model for inference when the latency or cost payoff justifies the added pipeline complexity and the validation effort, and confirm the optimised model still predicts correctly. For a heavily-served GPU model, TensorRT-style optimisation combined with dynamic batching can cut serving cost dramatically; for a lightly-used one, it is premature optimisation.

## Where this fits
You understand inference optimisation with TensorRT: rewriting the trained model (layer fusion, precision reduction, hardware-tuned kernels) for 2-5x faster serving with validated-equivalent predictions, worth it when latency or GPU cost matters, at the cost of a hardware-specific conversion step. Model-level speedup (TensorRT) plus serving-level batching (dynamic batching) are the two halves of efficient GPU serving. ===D5===
## Production inference at scale: Triton Inference Server
FastAPI is great for serving one model at moderate traffic, but production model serving at scale, multiple models, GPU efficiency, dynamic batching, high throughput, needs purpose-built infrastructure, and **Triton Inference Server** (NVIDIA's) is the standard. Triton is a dedicated model-serving system that provides, as built-in infrastructure, the things you would otherwise hand-build: **dynamic batching** (D3), support for **multiple models and frameworks** at once (PyTorch, TensorFlow, ONNX, TensorRT models side by side), **GPU sharing** across models, **concurrent model execution**, and serving metrics. You give Triton your models and a config, and it handles efficient, scalable inference serving for you.

## Why a specialised server beats rolling your own
The reason production teams use Triton (or similar, like TorchServe, KServe) rather than scaling up a FastAPI app is that efficient serving infrastructure is a large, hard problem you do not want to rebuild. Hand-rolling dynamic batching, multi-model management, GPU memory sharing, concurrent execution, and serving metrics in your own FastAPI code would be a major engineering project, error-prone and never as optimised as the dedicated server, exactly the build-vs-buy logic that favoured experiment trackers and orchestrators earlier. Triton provides all of it, tuned and battle-tested, so you focus on *your* models and the serving config rather than reinventing the serving engine. It also unifies serving: instead of a separate bespoke service per model, one Triton instance serves many models across frameworks efficiently on shared GPUs, which is both simpler to operate and far more cost-efficient at scale (better GPU utilisation across models). For a production ML platform serving many models to real traffic, this consolidation and efficiency is the whole point.

## When to use FastAPI and when to reach for Triton
The practical judgement, consistent with the track's simplicity discipline, is to match the serving infrastructure to your actual scale and not over-build. **FastAPI (with uvicorn)** is the right choice for a single model, moderate traffic, CPU or simple GPU inference, it is simple, fast to set up, and entirely sufficient, and reaching for Triton here would be heavy over-engineering (Triton is itself infrastructure to learn and operate). **Triton** (or another dedicated inference server) becomes the right choice when you genuinely need its capabilities: serving *multiple* models, needing dynamic batching for GPU efficiency at meaningful traffic, requiring high throughput, or running a serving *platform* for a team. The signal to graduate is concrete, your FastAPI serving is hitting GPU-efficiency or throughput limits, or you are managing many models, exactly the limits this week's D1 said FastAPI would eventually hit (slow models, dynamic batching needs). So the path is: start with FastAPI, and adopt Triton when the model speed, the GPU economics, or the number of models genuinely demands production serving infrastructure. Knowing both, and *when* to move from one to the other, is the serving-architecture judgement, the same start-simple-escalate-deliberately pattern as orchestrators (W15) and Kubernetes (W16).

## Where this fits
You understand Triton Inference Server: production infrastructure providing dynamic batching, multi-model multi-framework serving, and GPU efficiency out of the box, adopted when scale (multiple models, GPU throughput, high traffic) outgrows FastAPI's simple sufficiency. ===D6===
## The cold-start problem in serving
A serving challenge that bites in practice: the **cold start**. When a serving instance starts up, or scales from zero, or handles its first request after being idle, the *first* request is slow, because the system must do expensive one-time work before it can predict: load the (possibly large) model into memory, initialise the framework and GPU context, warm up caches. After that, subsequent requests on the now-**warm** instance are fast. The gap can be dramatic, the first request takes seconds (loading a multi-gigabyte model onto a GPU) while warm requests take milliseconds, and that slow first request is a real user experience and reliability problem.
```text
cold instance:  request 1 -> [load model, init GPU, warm caches] -> SLOW (seconds)
warm instance:  request 2,3,4... -> model already loaded -> FAST (ms)
```

## Why cold starts happen and where they hurt
Cold starts are the price of *not* keeping a serving instance permanently loaded and ready, and they appear precisely in the architectures that save money by scaling down. **Serverless / scale-to-zero** serving (which you saw cause cold starts in the AI-engineering deployment week, and which keeps FORGE's own Neon database cold) shuts instances down when idle to avoid paying for them, so the next request after idle pays the cold-start penalty, you traded standing cost for first-request latency. **Autoscaling** has the same issue: when traffic spikes and the system spins up *new* instances to handle it, those new instances are cold, so exactly when load is highest, some requests hit slow cold starts. And **large models** make it worse, the bigger the model, the longer it takes to load, so the cold-start penalty grows with model size. So cold starts hurt most in cost-optimised, elastic deployments serving large models, which is a very common production situation, and ignoring them means a fraction of users (the unlucky ones hitting a cold instance) get a badly slow experience.

## Managing the cold-start vs cost trade
The fix is a deliberate trade between **always-warm cost** and **cold-start latency**, and the techniques span that trade:
- **Keep instances warm:** run a minimum number of always-on instances (never scale fully to zero), or send periodic "keep-alive" requests so an instance never goes idle long enough to go cold. This eliminates cold starts at the cost of paying for idle capacity, the right choice when latency matters and you can afford the standing cost.
- **Pre-warm proactively:** when autoscaling, spin up and *warm* new instances (load the model, run a dummy inference) *before* routing real traffic to them, so users never hit a cold one.
- **Speed up the cold start itself:** make the model load faster (smaller/optimised model, faster storage for the model file, lazy-loading only what is needed), shrinking the penalty even when it occurs.
- **Accept it where appropriate:** for a low-traffic internal tool, scale-to-zero with occasional cold starts is a fine cost saving, the penalty rarely hits and rarely matters.
The judgement is to decide how much cold-start latency your use case can tolerate and spend accordingly, always-warm for latency-critical user-facing services, scale-to-zero for cost-sensitive low-traffic ones, and pre-warming for spiky autoscaled traffic. This is the same standing-cost-vs-responsiveness trade that runs through serving, made concrete, and handling it well is what keeps a cost-efficient elastic deployment from delivering occasional terrible latency.
